# ForkYou 分析规则

版本：1.0.0  
适用对象：任何执行 ForkYou 分析的 Agent。规则不绑定某个模型、IDE 或云服务。

## 0. 总目标

把一个开源项目拆成**可学习、可分享、可面试复述、可迁移到自己的项目**的知识包。

读者画像：

- Java 后端出身，做过运维实施，熟悉 Linux / Docker / K8s 的全栈程序员。
- 关注：计算机视觉、算法、性能、技术架构、底层原理、优化落地。
- 用途：技术分享、面试吹B、架构启发。

写作要求：

- 中文，密度高，少铺垫。
- 先给结论，再给证据。
- 不确定的写 `待查实`，不要编。
- 每个技术判断必须能落到 `文件:行号` 或官方来源。

## 1. 证据规则（硬约束）

1. 代码证据格式：`` `path/to/file.rs:123-145` ``，路径相对源码仓库根。
2. 外部链接格式：`https://github.com/<owner>/<repo>/blob/<commit>/<path>#L123-L145`。
3. 分支证据必须注明分支名：`origin/<branch>:path:line`。
4. 版本/star/license 以分析时的 GitHub API 或仓库文件为准，写日期。
5. 性能数字必须注明来源：官方 benchmark、代码里的常量、或本机实测。本机实测要写命令。
6. 推断必须标记：`推断：...`；没有证据的猜测标 `待查实`。
7. 不把 README 的宣传语当成架构事实；要回到代码。

## 2. 长度模式

| 模式 | 触发 | 正文总量 | 用法 |
|---|---|---|---|
| `lite` | 用户说“精简版/快速看” | 约 5k–8k 中文字 | 只保留定位、架构、代码地图、贡献入口 |
| `default` | 默认 | 约 1.2万–2.5万中文字 | 8 篇齐全，重点篇 3000–6000 字 |
| `deep` | 用户说“越详细越好/深挖” | 3万–6万中文字，不设硬上限 | 每篇都展开，增加代码走读、benchmark、历史 |
| 数字 | 用户说“写 8000 字” | 按数字执行 | 允许偏差 ±20% |

每篇建议：

- `01-positioning.md`：800–2000 字。
- `02-architecture.md`：2500–6000 字。
- `03-code-tour.md`：2500–6000 字。
- `04-deep-dive-*.md`：每篇 1500–4000 字，至少 2 篇；L3 至少 3 篇。
- `05-performance.md`：1000–3000 字；不适用时 300–800 字说明为什么。
- `06-branches.md`：800–2500 字。
- `07-contribute.md`：1000–2500 字。
- `08-takeaways.md`：1000–2500 字。
- `09-ops.md`：800–2000 字；不适用时短写。
- `README.md`：≤800 字。
- `guide.html`：以图为主，正文不超过 3000 字。

## 3. 固定文档结构

每个项目目录必须有：

```text
README.md
meta.json
01-positioning.md
02-architecture.md
03-code-tour.md
04-deep-dive-*.md   # 至少 2 篇
05-performance.md
06-branches.md
07-contribute.md
08-takeaways.md
09-ops.md
guide.data.json
guide.html
```

### 01-positioning.md

回答：

- 一句话是什么。
- 谁在什么场景下用它。
- 它要解决的痛点；没有它之前人们怎么做。
- 市场现有方案/竞品对比表：名称、定位、核心差异、license、成熟度。
- 为什么是现在：技术/生态/成本变化。
- 项目健康度：stars、fork、contributors、release 节奏、open issues、license、最近 commit。
- 应用地址/官网/安装包/文档入口。
- 一句话结论：值不值得学，适合谁学。

### 02-architecture.md

回答：

- 系统上下文：它和 OS、网络、其他设备、外部服务的关系。
- 模块地图：每个 crate/package/service 的职责。
- 数据流：从输入到输出的主链路；至少一张 Mermaid 图。
- 部署拓扑：进程、线程、服务、IPC、端口。
- 关键设计决策：问题 → 方案 → 代价 → 替代方案。
- 架构亮点：3–7 条，每条带代码证据。
- 读架构时最容易误解的点。

### 03-code-tour.md

回答：

- 仓库目录树（只列有意义的层，不贴 3000 个文件）。
- 构建/运行入口：从哪个文件开始。
- 主流程走读：请求/事件从 A 到 B，逐步列函数和文件。
- 先读的 8–12 个文件，按顺序，每个一句话“为什么读它”。
- 关键类型/结构体/trait/函数签名，带 `file:line`。
- 如果要加一个功能，改哪几个文件。
- 测试在哪里，怎么跑。

### 04-deep-dive-*.md

按项目内容选 2–4 个主题，不要硬凑。候选：

- 算法：调度、路由、匹配、压缩、检测、渲染、搜索。
- 性能：热路径、内存布局、零拷贝、批处理、缓存。
- 并发：线程模型、锁、channel、actor、背压。
- 协议：帧格式、版本、握手、加密、重放保护。
- 存储：数据模型、持久化、恢复、一致性。
- 安全：信任边界、权限、密钥、沙箱。
- 跨平台：OS 抽象、输入/显示/音频差异。
- 插件/扩展：接口、生命周期、隔离。
- 容错：重试、降级、故障恢复。

每篇固定结构：

1. 问题是什么。
2. 朴素做法为什么不够。
3. 这个项目怎么做（核心机制）。
4. 代码证据（3–8 个 `file:line`）。
5. 复杂度/性能/边界条件。
6. 取舍与局限。
7. 我能偷什么（可迁移的设计）。

### 05-performance.md

- 性能敏感路径清单。
- 时间/空间复杂度。
- 关键常量、阈值、缓冲区大小。
- 官方 benchmark 或本机实测；写命令。
- 优化手法：零拷贝、对象池、批处理、锁粒度、SIMD、缓存、异步。
- 瓶颈与反例：哪些优化其实没用。
- 如果项目不是性能型，写清楚“不适用”的原因，不要硬编。

### 06-branches.md

- 分支列表、默认分支、每个分支的用途。
- 默认分支 vs 其他分支：ahead/behind、变更文件数、关键 commit。
- 分支差异的实际影响：API、协议、平台、发布流程。
- 读代码建议：先读哪个分支，哪些分支可以忽略。
- 分支风险：未合并、实验性、长期偏离。

数据来源：`_cache/work/<id>/snapshot.json` 和本地 `git diff`。不要靠猜。

### 07-contribute.md

- 支持的 OS/工具链版本。
- 本地构建、运行、测试、lint 命令；从 CI 文件反推。
- 依赖服务/系统权限（macOS 辅助功能、Windows 服务、虚拟音频设备等）。
- CI 矩阵和 release 流程。
- Issue/PR 规则；项目是否接受外部 PR。
- 3–5 个适合新手的入口（good first issue、文档、测试、平台适配）。
- 贡献前必须知道的坑。

### 08-takeaways.md

- 5–10 条可迁移想法，固定格式：
  - 问题 →
  - 做法 →
  - 为什么好 →
  - 怎么用到我的项目。
- 面试 Q&A 卡片 6–8 张：问题、30 秒答案、追问。
- “吹B一句话” 3–5 条，但要能落地，不要空话。
- 局限与不该抄的地方。

### 09-ops.md

- 安装/部署方式。
- 配置项、端口、数据目录、日志位置。
- 资源需求（CPU/内存/磁盘/网络）。
- 可观测性：日志、指标、诊断包。
- 故障模式与排查步骤。
- 安全注意事项。
- 升级/回滚。

## 4. 写作风格

- 用短句。先结论后解释。
- 多用表格做对比，多用编号做步骤。
- 代码块标语言。
- 不写“众所周知”“显而易见”。
- 不复制 README 大段；要转成自己的话。
- 每篇开头写“这篇回答什么问题”，结尾写“一句话记住”。

## 5. guide.html 规则

固定 8 段，没内容就自动隐藏：

1. Hero：项目名、一句话、应用地址、关键 metadata。
2. 60 秒心智模型：3 张卡。
3. 架构图：可点击的 SVG 模块，侧栏解释。
4. 核心机制：3–8 步，可播放/上一步/下一步，联动高亮架构节点。
5. 代码地图：先读的 8–12 个文件。
6. 跑起来：可复制命令。
7. 分支与贡献：分支 diff 卡 + 贡献入口。
8. 吹B卡片：6–8 张翻面问答。

技术约束：

- 单文件 HTML，离线可打开。
- 所有图用内联 SVG，不引用外部图片。
- 动画基础用 CSS；anime.js 作为增强，CDN 用 BootCDN，Staticfile 兜底；加载失败不影响阅读。
- 响应式；键盘可操作；尊重 `prefers-reduced-motion`。
- 数据来自 `guide.data.json`，由 `render-guide` 注入模板，不手写 HTML。

## 6. 分支分析

- 默认分支：完整读。
- 其他分支：先看 `git diff --stat`、`git log`、关键文件 diff；不要假设它们会合并。
- 分支差异写进 `06-branches.md`，不要散落在其他文档。
- 如果分支只是 CI/发布分支，明确写“无代码差异”。

## 7. 外部研究

- 最多 5 个来源（`max_sources`）。
- 优先：官方文档、论文、release notes、作者博客、Issue/PR。
- 每个来源记录：标题、URL、日期、用它支撑哪个结论。
- 不把搜索结果当事实；要回到原文。
- 来源列表放 `guide.data.json.sources` 和 `01-positioning.md` 末尾。

## 8. 安全与许可证

- 不复制 `.env`、token、密钥、个人信息；发现即脱敏。
- 代码引用每段 ≤30 行；不整文件复制。
- 引用必须带 upstream commit 链接和 license 标注。
- GPL/AGPL 项目：只引用必要片段；不把大段代码放进 ForkYou。
- 不执行来源不明的脚本；只读分析。

## 9. 发布

- 先 `validate`，再 `publish`。
- 一个项目一个 commit；消息格式：`analyze(<repo>): <depth> @ <short-sha>`。
- 不 force push。
- 发布前 `git status` 必须干净或只包含本次项目文件。
- 失败时保留旧文档，manifest 标 `failed`，不要删除已有分析。

## 10. 质量检查清单

- [ ] 8 篇文档齐全，`04` 至少 2 篇。
- [ ] 每个技术结论有 `file:line` 或来源。
- [ ] 竞品对比表至少 3 个方案。
- [ ] 架构图和数据流能对应到代码。
- [ ] 分支差异有 diff 数据。
- [ ] 贡献命令来自 CI/README，不是编的。
- [ ] guide.html 能本地打开，8 段可交互。
- [ ] 没有 TODO、没有占位符、没有秘密。
- [ ] `meta.json` 和 manifest 一致。
