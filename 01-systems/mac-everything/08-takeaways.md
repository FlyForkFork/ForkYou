# 08 收获：可迁移的想法

> 这篇回答：哪些设计能偷，面试怎么讲。

## 5 条可迁移想法

### 1. 先缩候选，再谈并行

- **问题**：600 万条记录全表扫描，线程开满也要几百毫秒。
- **做法**：名称 trigram、扩展名索引、目录路径三路候选，取最小集合；只有候选 ≤ 总数 1/10 才用（`MacEverything/Core/SearchEngineAdvancedQuery.cpp:629-750`）。
- **为什么好**：把“并行度”换成“少做事”，收益更大且更稳。
- **怎么用到我的项目**：任何搜索/推荐/日志查询，先建一个“能把候选缩到 1% 的索引”，再考虑多线程。

### 2. 查询计划要能解释自己

- **问题**：用户只觉得“有时快有时慢”，开发者不知道为什么。
- **做法**：`QueryTimingInfo` 记录 `lockWaitMs / trigramMs / phase1Ms / phase2Ms / sortMs / candidates / usedTrigram / searchPath`，HTTP 直接返回 `timing`（`MacEverything/Core/SearchEngine.h:86-101`、`MacEverything/Core/HttpServer.cpp:409-478`）。
- **为什么好**：性能问题从“猜”变成“看字段”；候选数、锁等待、排序各占多少一目了然。
- **怎么用到我的项目**：给每个慢查询打结构化 timing，不要只打总耗时。

### 3. 快照分页，而不是“全量结果 + 客户端切片”

- **问题**：600 万条结果不可能一次跨语言拷贝；滚动时还要保持顺序稳定。
- **做法**：`MEQuerySnapshot` 只存 ID 数组 + generation，`resultsAtOffset` 按页物化（`MacEverything/Bridge/MacSearchBridge.mm:7-32`）。
- **为什么好**：内存与延迟都按页付；generation 变化时能明确重查，而不是返回错位数据。
- **怎么用到我的项目**：API 分页返回“查询令牌 + 游标”，不要每页都重新跑查询。

### 4. 把“重写”做成可整体替换的快照

- **问题**：原地更新大索引文件，崩溃后可能半新半旧。
- **做法**：v6 写临时文件 → fsync → rename；WAL 只追加，满了再 full rewrite（`MacEverything/Core/FlatIndexWriter.cpp:392-402`、`MacEverything/Core/IndexPersistence.cpp:114-200`）。
- **为什么好**：任何时刻磁盘上都有一份完整旧文件或完整新文件，恢复逻辑简单。
- **怎么用到我的项目**：配置、缓存、模型权重，凡是“大块可重建数据”，都用 copy-on-write + atomic rename。

### 5. 事件先翻译成领域操作，再进核心

- **问题**：FSEvents、inotify、USN Journal 的事件语义各不相同，直接塞进索引会让核心到处 `if platform`。
- **做法**：`collectFSEventMutations` 统一翻译成 `Add/Remove/Update/REMOVE_TREE/rescanDirs`（`MacEverything/Core/ServiceEngine+FSEvents.cpp:44-123`）。
- **为什么好**：平台适配层可单测；核心只处理领域操作。
- **怎么用到我的项目**：文件同步、缓存失效、消息队列消费，都先做“事件 → 领域命令”的翻译层。

## 面试 Q&A

### Q：这个项目怎么在 600 万条记录上做到毫秒级搜索？

**30 秒答案：** 名称 trigram 和扩展名索引先把候选缩到很小，再按编译期特化的 `simdContains` 循环扫描；复杂条件走 AST 求值。纯元数据查询则全表并行，用 16 路 liveness 位掩码跳过空记录。每线程只保留 Top-K，合并后排序。

**追问：** 如果 trigram 候选太多怎么办？——超过总数 1/10 就放弃该候选集，退回全量扫描；宁可变慢，也不构建巨大候选数组。

### Q：v6 + WAL 怎么保证崩溃一致性？

**30 秒答案：** v6 全量写临时文件，fsync 后 rename，旧文件在 rename 前始终完整；WAL 是追加写的 `WAL1` 记录流，每条带 CRC，启动时逐条回放，坏条目截断并保留之前记录。WAL 超过 50 MB 或 tombstone 超过 25% 就触发全量重写。

**追问：** 会不会丢最近 64 条？——会，`fsync` 每 64 条一次，这是吞吐与丢失窗口的取舍；`fflush` 每条都做，进程崩溃不丢，断电可能丢最多 63 条。

### Q：为什么用 SoA 而不是 `vector<Record>`？

**30 秒答案：** 查询只读 `types_`、`sizes_`、`modTimes_` 或名称池，不读整条记录；SoA 让扫描只碰需要的列，缓存命中率高，也方便 SIMD。`NarrowColumn` 再把 64 位字段压成 32 位，溢出值走旁表。

**追问：** 更新一条记录怎么办？——按列写对应下标，路径表用“目录规范号 + 文件名”定位；批量更新一次加锁。

### Q：FSEvents 事件风暴怎么处理？

**30 秒答案：** 先按批翻译成领域操作，`REMOVE_TREE` 覆盖的子路径直接丢弃；整批一次 `batchMutate` 加锁。目录级变化 5 秒 debounce、300 秒节流，避免反复重扫。

**追问：** journal 被截断怎么办？——`FileSystemWatcher` 检测到 `journalTruncated`，上层退回全量扫描，保证不丢文件。

### Q：为什么查询快照要带 generation？

**30 秒答案：** 索引压缩会重编号记录，旧 ID 可能指向新记录。快照在分页时校验 generation，不一致就让上层重查，避免返回错位结果（`MacEverything/Bridge/MacSearchBridge.mm:404-421`）。

**追问：** 重查会不会闪？——会有一帧刷新，但比展示错误文件好；分页大小 100，重查成本低。

### Q：这个项目最大的性能瓶颈是什么？

**30 秒答案：** 宽路径查询（30–50 ms）和全量保存（约 712 MiB 写放大）。前者是线性目录扫描，后者是 v6 整文件重写；项目自己也在审计里标为未解决。

**追问：** 怎么改？——路径查询可以加路径 trigram（项目曾移除常驻路径 trigram，说明内存与延迟要再平衡）；保存可以改增量 section 或双缓冲。

### Q：如果让你重写，会保留什么、改什么？

**30 秒答案：** 保留候选集竞争、v6 列式快照、快照分页；改掉全量重写（改增量 section）、把路径查询也建索引、把 1/10 阈值做成可配置。

**追问：** 为什么不直接上 SQLite？——SQLite 解决事务和 B 树，但解决不了 trigram posting 的列布局与零拷贝加载；引入后仍要自己写索引层，收益不明确。

## 吹B一句话

1. “它把 638 万条文件记录压到 573 MiB，还能在 0.93 ms 内找出所有 Swift 文件。”
2. “查询先在三路索引里竞选最小的候选集，再并行验证——不是无脑多线程。”
3. “v6 文件用 11 个 section 存列，WAL 每条带 CRC，崩溃恢复能保留坏条目之前的全部记录。”
4. “FSEvents 先翻译成领域操作再批量加锁，目录变化用 5 秒 debounce 吃掉事件风暴。”
5. “同一个 C++ 引擎，同时驱动菜单栏 App、无头 daemon 和 MCP 服务器。”

## 不该抄的地方

- **50 MB WAL 上限 + 64 条 fsync**：对高写入场景太粗；应改成按字节/时间自适应，并暴露配置。
- **1/10、1/4 的魔法阈值**：没有基准驱动的自动调参；不同数据规模下最优值会变。
- **全量重写 712 MiB**：项目自己承认写放大未解决；新项目应直接设计增量 section。
- **`kAppVersion = "1.1.0"` 残留**：版本单一来源没做好，任何项目都该避免多处硬编码版本。
- **`Makefile` 不跟踪头文件依赖**：改 `.h` 不重编是隐蔽坑；用 CMake/Ninja 或 `-MMD` 自动依赖。

**一句话记住：** 最值得偷的是“候选集竞争 + 列式快照 + 事件翻译层”，最不该抄的是全量重写和硬编码阈值。
