# 05 性能：热路径、常量、实测

> 这篇回答：哪里最贵、贵在哪、有哪些实测数字、哪些是拍脑袋的常量。

## 性能敏感路径

按用户可感知程度排序：

1. **起播**：从点开一条剧到第一帧出现。链路上有三次串行等待——业务 API（取播放地址）→ 清单下载 → 首个分片下载。
2. **seek**：拖动进度条松手到画面更新。短剧用户的高频操作，`docs/playback-investigation-20261108.md` 的样本里 9 次定位有 8 次是点击。
3. **翻页**：竖滑到下一条。理想是零等待，实际取决于预取是否命中。
4. **封面**：列表滚动时的图片加载。第三方客户端最容易在这里丢帧。

## 复杂度

| 路径 | 复杂度 | 说明 |
|---|---|---|
| `rewrite_playlist` | O(行数 × 单次 URL 解析) | 主清单 20~40 行，子清单几百行 |
| `aes_cbc_decrypt` | O(字节数) | AES-128-CBC，Rust 实现约几百 MB/s |
| `edge_operation` | O(1) | 字符串前缀匹配，用于日志标签 |
| `resolve_target` | O(1) 次 DNS + O(n) 地址校验 | n 是 DNS 返回的地址数，通常 1~4 |
| `client_for` | 均摊 O(1) | HashMap 查找；缓存满 64 时整体清空 |
| `cache_put` | O(1) | 满时随机删一个 key，非 LRU |
| Feed 详情预取 | O(3) 并行请求 | 当前条 ±1 |

真正值得注意的不是算法复杂度，而是**串行次数**。起播链路上有 3~4 次串行网络往返，每次 20 秒超时上限（`src-tauri/src/net.rs:128-149`），最坏情况下的等待远大于任何计算开销。

## 关键常量/缓冲区

### hls.js 缓冲（`src/components/VideoSurface.tsx:184-210`）

| 常量 | 值 | 意图 |
|---|---|---|
| `maxBufferLength` | 30s | 正常缓冲目标 |
| `maxMaxBufferLength` | 60s | 上限（网络好时不无限拉） |
| `backBufferLength` | 30s | 回退缓冲，影响「往回拖」的命中率 |
| `maxBufferHole` | 0.5s | 小于此值的空洞跳过而非等待 |
| `highBufferWatchdogPeriod` | 2s | 缓冲卡住检测周期 |
| `nudgeOffset` | 0.25s | 卡住时向前推的距离 |
| `nudgeMaxRetry` | 6 | 最多推 6 次（共 1.5s） |
| `manifestLoadingTimeOut` | 20s / 4 次 | 清单加载 |
| `levelLoadingTimeOut` | 20s / 4 次 | 子清单加载 |
| `fragLoadingTimeOut` | 25s / 6 次 | 分片加载 |
| `fragLoadingRetryDelay` | 400ms | 分片重试间隔 |
| `startFragPrefetch` | true | 起播时预取首个分片 |

30/60/30 这组数字偏保守。对比 hls.js 默认（`maxBufferLength: 30`，`maxMaxBufferLength: 600`），项目把上限从 600s 砍到 60s。推断：短剧单集通常 1~3 分钟，缓冲超过一集没意义，且移动端内存紧张。

`maxBufferHole: 0.5` 配合 `nudgeOffset: 0.25` 是个组合拳：小于 0.5s 的空洞不等待（直接跳），播放卡住时向前推 0.25s 试探。这套参数适合「分片边界有轻微不连续」的流。

### Rust 侧缓存

| 缓存 | 容量 | 淘汰 |
|---|---|---|
| `IMG_CACHE` | 240 条目 | 满则随机删一个 |
| `PL_CACHE` | 60 条目 | 同上 |
| `KEY_CACHE` | 120 条目 | 同上 |
| `SEG_CACHE` | 36 条目 + 4MB | 同上，超 4MB 不入 |

`SEG_CACHE` 的 36 条 × 4MB 上限意味着**最坏情况 4MB 而不是 144MB**——因为每条独立判断，总量约束靠单条上限而非总容量。这是个容易误读的设计：`SEG_CACHE_MAX_BYTES` 是单条上限，不是总和上限。

## 基准/实测

数据来自 `docs/playback-investigation-20261108.md`（2026-11-08 的一份真实日志分析，602 行 debug.log + 2760 行 playback.log，跨多个进程）。**这是单一样本，不是基准测试**，作者本人也强调「不能当作单次复现的故障率」。

### seek 耗时（9 次定位）

| 指标 | 值 |
|---|---|
| 各次耗时 | 1518、2986、430、547、1118、818、2401、1953、1282 ms |
| 中位数 | 1282 ms |
| 输入构成 | 8 次点击、1 次拖动 |
| 首帧恢复 | 9/9 全部有匹配的 `seek.resumed`，无超时 |

最慢的一次（2986ms）拆解：13:44:09.656 发起 → 约 3ms 后开始请求目标分片 → 下载 2603ms → 约 10ms 后完成入缓冲 → 2986ms 收到首帧。

**结论：seek 的耗时几乎全部在分片下载，不在 seek 逻辑本身。** 这也印证了「先完整下载再返回」的设计代价（见 [04](04-deep-dive-media-proxy.md)）。

### 分片入缓冲（64 个样本）

| 指标 | 值 |
|---|---|
| 中位数（`hlsFragLoaded` → `hlsFragBuffered`） | 11 ms |
| 最大值 | 77 ms |

**结论：入缓冲不是瓶颈。** 但作者提醒：「它不等同于测量界面帧率」——入缓冲快不代表渲染流畅。

### 起播（3 次）

| 指标 | 值 |
|---|---|
| 播放器加载源 → 首个 `playing` | 3.68s、3.35s、4.62s |

注意这个数字**不含**业务 API 耗时，也不含「进入详情页到播放器挂载」的间隔（吃瓜详情需要用户点击播放）。

### 图片（封面）

| 指标 | 值 |
|---|---|
| 网络尝试中位耗时 | 约 1.55 s |
| 最长 | 3.63 s |
| 失败重试 | 10 次失败后重试恢复，最终 HTTP 200 |

图片是列表滚动的隐藏成本。1.55s 的中位数意味着首屏之后必须靠 `IMG_CACHE`（240 条）兜，否则滚动会持续掉帧。

## 优化手法

### 已实现的

1. **三路详情预取**（`Feed.tsx:334-343`）：`index-1 / index / index+1` 并行请求。这让「滑到下一条」时的详情已在内存，把起播链路的第一次等待消掉。
2. **`startFragPrefetch: true`**：清单解析完就预取首个分片，不等 `startLoad`。
3. **客户端缓存 30s**：同一 host 的 TLS 连接与 DNS 结果复用 30 秒，避免每次请求重新握手。
4. **`heal_client` 3 秒节流**：代理切换后立刻重建客户端，但不会因为连续失败反复重建。
5. **封面双档缓存**：内存 240 条 + HTTP `max-age=86400`。
6. **`Accept-Ranges: bytes`**（`src-tauri/src/media.rs:301-313`）：让 WebView 可以对分片做 Range 请求，虽然 Rust 侧是整段下载，但头部声明正确不会阻塞。
7. **`translate3d` 做变换**：Feed 的缩放/平移用 GPU 合成层，避免触发重排。

### 明显还缺的

1. **流式转发**。当前是「下载完整分片再返回」，`docs/playback-investigation-20261108.md` 自己指出这点。改成边下边转发能把 seek 的 2.6s 下载时间转化为渐进式起播。代价是失去 `Content-Length`、要处理 Range、要处理客户端中断。
2. **`SEG_CACHE` 太小**。36 条、单条 4MB、随机淘汰。一个 2 秒分片的短剧一集 60~90 个分片，36 条覆盖不到一半，回退拖动基本全 miss。`backBufferLength: 30` 让 hls.js 保留 30 秒缓冲，但 Rust 侧缓存更小，两者不匹配。
3. **图片没有优先级**。`img` 全是 `loading="lazy"`（`src/html.ts:76-116`），但 Feed 首屏的封面和后续的封面用同一优先级。首屏可见封面应该 eager。
4. **`clear_caches` 是唯一清空入口**，没有按容量自动清理。长时间使用后内存占用只增不减（虽然有 240/60/120/36 的条目上限，但分片单条可达 4MB）。

## 瓶颈与反例

**反例 1：不要用「首页 HTTP 200」判断线路可用。**
`docs/playback-investigation-20261108.md` 明确写：「现有网络自检/线路测速只检查站点首页，HTTP 200 不能证明业务网关正常」。线路探测打的是 `{url}/`（`src-tauri/src/lines.rs:72-87`），而业务请求走的是 `/api/edge/request`。两者可达性不同。

**反例 2：不要把「分片入缓冲 11ms」当成「播放流畅」。**
入缓冲是 MediaSource 的操作，与渲染帧率无关。真正的卡顿在合成、解码、纹理上传。

**反例 3：不要指望重试救回 404。**
`retryable_error`（`src-tauri/src/net.rs:380-398`）里 401 不重试、策略类错误不重试；`docs/playback-investigation-20261108.md` 的修正是「HTTP 404、不可重试的 4xx、权限和安全拒绝直接结束」。重试只对 408/425/429/5xx 和超时有效。

**反例 4：30 秒客户端 TTL 不是缓存。**
`docs/media-cache-audit-20261108.md` 专门澄清：「网络层新增的 30 秒 `CLIENT_TTL` 用于 HTTP 客户端/DNS 检查结果复用，不是封面或播放列表内容缓存的有效期」。把两者混为一谈会得出错误的容量规划。

**一句话记住：** HGhub 的性能瓶颈不在代码里，在「先下载完整分片再返回」这一个决定上——seek 中位数 1282ms 里有 2603ms 的那个样本，全部耗在下载。
