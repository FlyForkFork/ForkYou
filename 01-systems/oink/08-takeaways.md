# 08 收获：可迁移的想法与模拟面试

## 这篇回答什么问题

如果只从 Oink 带走五样东西，带哪五样？如果面试一个"做过 Oink 的人"，会问什么、怎么答？

> **方法说明**：RULES 要求 08 由"面试官"子代理出题、"面试者"子代理作答。本轮 subagent 因委派深度限制不可用（`subagent depth 2 exceeds maxDepth 1`），**双 Agent 流程未执行**；以下问答由主 Agent 基于源码证据整理，属单 Agent 模拟。

## 可迁移的想法

### 1. 纯状态机 + 输出队列（问题→做法→为什么好→怎么用）

- **问题**：输入路由要和 OS 时钟、网络、UI 全解耦，否则没法测、没法复现。
- **做法**：`Router` 不读系统时钟，所有时间由调用方以 `Micros` 传入（`router.rs:83`）；不直接产生副作用，所有动作进 `Vec<Output>`，由 `drain_outputs()`（`:1575`）取出执行。
- **为什么好**：整个路由逻辑可以用"一串输入 + 一串时间戳"驱动，单元测试不需要 mock 任何系统调用。`crates/oink-routing` 有 3.6 万行，大量是测试。
- **怎么用**：任何"策略 + 副作用"混杂的模块（限流器、调度器、审批流）都可以拆成"纯决策函数 + 命令队列"。

### 2. 线程所有权表（问题→做法→为什么好→怎么用）

- **问题**：实时系统最怕不可预测的锁等待。
- **做法**：`threads/mod.rs:1-17` 列出 6 个线程，每个子系统只有一个 owner；线程间只有三种东西——每流每端一个队列、整块替换的只读快照、小定长命令。
- **为什么好**：没有共享锁就没有锁竞争；快照读永不阻塞；命令足够小，队列不会成为内存黑洞。
- **怎么用**：先画"谁拥有什么状态"的表，再写代码。表画不出来就说明设计还没想清楚。

### 3. 分段时间预算（问题→做法→为什么好→怎么用）

- **问题**：一轮循环里多种工作，怎么保证重要的先做、空闲时不浪费？
- **做法**：`[OWN 100µs, INTERACTIVE 250µs, NORMAL 150µs]` 三个截止点，前段剩余时间自动给后段（`link/mod.rs:87-90`）。
- **为什么好**：比固定配额适应负载，比"全做完再排优先级"可预测。
- **怎么用**：任何 event loop 都可以套这个结构——自己的维护工作、交互请求、后台任务三段。

### 4. 身份来自证书结构，不来自字节匹配（问题→做法→为什么好→怎么用）

- **问题**：怎么在不依赖 CA 的 P2P 里确认对方身份？
- **做法**：自签 Ed25519 证书，SPKI 就是设备 ID；`device_id_from_cert` 先解析 x509 结构再取 SPKI，注释写明"subject/extension 里的匹配字节序列永不算身份"（`tls.rs:24`）。
- **为什么好**：把"身份"锚在密码学结构上，而不是"在某处找到了这串字节"。
- **怎么用**：任何从证书/令牌提取身份的地方，都先解析结构再取值，永远不要 `memmem`。

### 5. 提示 ≠ 命令（问题→做法→为什么好→怎么用）

- **问题**：A 机告诉 B 机"该解锁了"，B 机怎么防伪造/重放？
- **做法**：提示只带 epoch；B 机反向质询 A 机"你现在锁没锁"；`(Boot, epoch)` 做重放栅栏；两段式确认，2 秒窗口（`auto_unlock/sync.rs`）。
- **为什么好**：即使 A 完全失陷，也只能"请求"不能"命令"；重放的消息在栅栏处被拒。
- **怎么用**：所有跨进程/跨设备的敏感动作，都设计成"请求 + 独立验证"，不要"通知 + 执行"。

### 6. 只在产生副作用的一侧做抑制（问题→做法→为什么好→怎么用）

- **问题**：剪贴板同步会回声，怎么去重又不丢内容？
- **做法**：只在发送侧抑制；接收侧收到 offer 一律写入；marker 优先于内容哈希；unknown 永远不算重复（`dedupe.rs:1-26`）。
- **为什么好**：误判的代价从"用户丢内容"降级为"多发一次"。
- **怎么用**：缓存、去重、限流、幂等——先问"错了会怎样"，把抑制放在错得起的一侧。

### 7. 设置后立刻读回（问题→做法→为什么好→怎么用）

- **问题**：向 OS 申请实时调度/QoS，怎么知道真的生效了？
- **做法**：设置完读回，之后每 5 秒复查；不一致就 `demoted += 1`（`realtime.rs:1-11`）。
- **为什么好**：把"配置"变成"可观测事实"，性能退化有数字可查。
- **怎么用**：任何 `set_*` 类系统调用（优先级、缓冲区、超时）都加一次读回和周期性复查。

## 面试 Q&A 卡

### Q1：为什么不用 Deskflow 的架构，要从零写一个？

**30 秒第一人称答案**：Deskflow 的模型是"一台 server 持有全局布局，client 只是被控端"，所以必须指定控制端，布局也是单点的。Oink 要"每台设备持有自己的布局视图、指针跟着人走"，README 写"无需指定控制端"（`README.md:40-41`）。核心模型不同，复用它的代码反而是负担；加上它 GPL-2.0 与我的 GPL-3.0-only 不兼容，所以从零写。

**追问**：怎么保证两台设备的布局视图一致？——协议同步布局对象（`StreamKind::LayoutProfiles` 13/14/15），但本地投影独立（`v1/layout.rs`：`DevicePlacement` key 5 不跨冻结几何边界）。

### Q2：为什么路由要设计成"不读时钟"的纯状态机？

**30 秒第一人称答案**：因为我要能测。输入路由的 bug 几乎都是时序 bug——"按住 Shift 跨屏时按键丢了"、"快速来回移动时焦点跳到第三台"。如果 Router 自己读 `Instant::now()`，这些场景就没法在单测里复现。所以我让调用方把 `Micros` 传进来（`router.rs:83`），Router 只做决策，输出 `Vec<Output>`，副作用由外面执行。

**追问**：超时逻辑怎么办？——`next_deadline()`（`:1586`）告诉调用方下次何时叫它。

### Q3：线程间为什么只有三种通信方式？

**30 秒第一人称答案**：因为锁的等待时间不可预测。一个实时线程如果等一把普通线程持有的锁，它的延迟就取决于那个线程什么时候被调度——这直接把实时性毁了。所以我规定线程间只有三种东西：每流每端一个队列（单向、有界）、整块替换的只读快照（永远可读）、小定长命令（`threads/mod.rs:1-17`）。

**追问**：快照复制不贵吗？——配置数据一秒变几次、一秒读几千次，复制成本远低于锁的成本。

### Q4：500µs 一轮，超了怎么办？

**30 秒第一人称答案**：不怎么办——超了就记一笔。`runtime.rs:270-310` 里 `over_budget` 计数、`late_rounds`/`late_max` 统计，还有 `realtime::read_back()` 和 `schedule.applied` 比对，不符就 `demoted += 1`。我不做自动降级或扩容——自动策略在实时系统里往往比问题本身更糟，数字暴露出来由人判断。

**追问**：用户看到什么？——诊断包里有这些计数（`crates/oink-agent/src/diagnostics/`，30 分钟环形记录）。

### Q5：为什么可靠性完全交给 QUIC，不自己写 ARQ？

**30 秒第一人称答案**：因为自研 ARQ 是最容易写错的东西——重传时机、拥塞窗口、流控窗口、乱序重组，每一项都有大量边界条件，而且 bug 往往只在弱网下出现。QUIC 已经把这些做对了，我只需要选"这条消息要 Reliable 还是 Datagram"。`Delivery` 只有两档（`router.rs:94`），就是这个约束的直接体现。代价是我不能做"部分可靠"（比如可靠但允许乱序），但目前没有这个需求。

**追问**：QUIC 的开销能接受吗？——局域网里 QUIC 的握手和头部开销可以忽略，`SEND_WINDOW` 还特意从 10MiB 收到 2MiB 来限制排队延迟（`qos.rs`）。

### Q6：自动解锁为什么要反向质询？直接信同伴不行吗？

**30 秒第一人称答案**：因为同伴可能失陷——攻破 A 就等于攻破整个组。所以我让 B 收到提示后，反向问 A"你现在到底锁没锁"（`auto_unlock/sync.rs:1`）。A 的回答还要过 `(Boot, epoch)` 重放栅栏（`:144-160`），同一个 boot 下 epoch 必须更大。再加 2 秒回复窗口和两段式确认（`:183`），重放和慢速伪造都挡得住。

**追问**：多一个 RTT 值得吗？——解锁不是高频操作，多 50ms 换"同伴失陷不等于全组失陷"。

### Q7：剪贴板去重为什么不用内容哈希做首选？

**30 秒第一人称答案**：因为 v1 的 offer 不带 digest，要算哈希就得读内容——而内容可能是 Universal Clipboard 的 promise，读它等于触发一次跨设备拉取，甚至可能拉不到。所以首选是 marker：Oink 写出的每个 clip 带一个私有格式，字节只表示这个 clip 的身份（`dedupe.rs:1-26`）。marker 跟着剪贴板被拷回来时，我只要读 marker 就知道是回声，不用碰内容。内容哈希只是没有 marker 时的 fallback，而且只在发送侧用。

**追问**：marker 被别的同步器剥了怎么办？——退化为内容比较；如果内容也不可比，按 unknown 处理，unknown 永远不算重复。

### Q8：如果重做，你会改什么？

**30 秒第一人称答案**：三点。第一，`oink-agent` 157765 行太大了，我会更早把 `auto_unlock`、`paste_file` 这些拆成独立 crate。第二，Windows 的解锁逻辑是 819 行 C++，和 macOS 的 1085 行 Rust 几乎不共享，我会定义一层更薄的平台接口，让 policy 部分只写一遍。第三，我会更早加 `c0_compat` 这种协议兼容 fixture——0.3.5 要兼容 0.3.0，这个测试是后来补的。

**追问**：有什么是你不会改的？——纯状态机 Router、线程所有权表、QUIC 不自己写 ARQ。这三条是根，改了就不是这个项目了。

## 吹 B 一句话（3–5 条）

1. "这个项目的路由是一个 4773 行的纯函数——不读时钟、不碰系统、所有副作用都排队，所以它能被单测驱动到每一个时序分支。"
2. "它的网络层没有一行重传代码：可靠性全给 QUIC，自己只负责'谁先发'和'什么时候切回直连'。"
3. "它的自动解锁连'同伴说解锁了'都不信——必须反向质询 + `(Boot, epoch)` 重放栅栏 + 2 秒窗口，把跨设备解锁做成了挑战-应答协议。"

## 局限与不该抄的地方

- **单人维护**：contributors 只有 `hachiwii`，0.3.5 发布 build 号 113，bus factor = 1。
- **平台假设深**：macOS Keychain/TCC 与 Windows DPAPI/服务模型各写一套，移植 Linux 要重写信任层。
- **`oink-agent` 过大**：15.7 万行单 crate，是历史积累而非设计目标。
- **`credential-provider` 不在 workspace**：构建链有隐藏依赖，新人不看 CI 不会发现。
- **无 benchmark**：性能结论只能靠常量推断，没有可复现的延迟数字。
- **不该抄的**：单人项目的发布节奏与双平台专用代码。

## 一句话记住

Oink 最值得偷的不是任何一行代码，而是三条纪律：**决策与副作用分离、状态有唯一 owner、敏感能力的每一次使用都要重新授权**。
